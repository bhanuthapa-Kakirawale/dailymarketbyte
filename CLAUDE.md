# Daily Byte — project guide for Claude Code

Automated 45-60s faceless YouTube Short: recap of the previous Indian (NSE) market session for traders.
Duration follows the content - a sparse session makes a shorter video, never padding.
Runs Mon–Fri 07:40 IST on GitHub Actions, uploads to YouTube. Informational only, never advice.

## Commands
- `python main.py --demo` — offline render with synthetic data (red "DEMO DATA - NOT REAL" badge). Use this to test any visual change.
- `python main.py` — real data, no upload. `--upload` uploads; `--force` ignores holiday/already-posted checks.
- `python upload.py --auth` — one-time YouTube OAuth (creates token.json).
- `python main.py --mode premarket [--session-date YYYY-MM-DD] [--frames-only]` — PRE-MARKET V1 "before the bell" Short (never uploads). `python render_pre_phase1.py` renders the real + synthetic validation scenarios to `output/pre_phase1/`.
- `python main.py --mode report [--session-date D] [--skip-radar]` — REPORT job: canonical report for the latest FINAL session + intelligence + Radar, no video, idempotent. `python main.py --mode premarket --shadow` — PRE shadow run into `output/pre_shadow/<date>/` (never uploads). `python validate_pre_production.py [--connectivity-only]` — readiness pack / reachability diagnostic. Schedule: docs/PRODUCTION_SCHEDULE.md.
- Verify a render: `ffprobe` duration must land inside `editorial.MIN_SHORT_DURATION`..`MAX_SHORT_DURATION` (15-70s) and normally 45-60s; extract frames with `ffmpeg -ss <t> -i out.mp4 -frames:v 1 f.png` and look at them.

## Architecture
- `main.py` — orchestration, ticker items, YouTube metadata, demo data, safety checks, and the four publication gates. What the video *says* and how long each scene runs is no longer here - that moved to `editorial/`.
- `market.py` — yfinance data (`history`, `get_movers`, `get_globals`, `get_sectors`), NSE website client (`NSE`, `nse_all_indices`, `fii_dii_nse`), technicals in `analyze()` (EMA20/50, RSI14, swing-based support/resistance, trendline, floor pivots).
- `news.py` — Google News RSS (free) + Gemini free API with Google Search grounding (`ask_gemini`). `ai_pass()` is the single combined Gemini call per run (market facts: GIFT Nifty/FII-DII/Brent/independent Nifty close, each validated by date + range; mover/Nifty move reasons; today's events) - kept as one request instead of three separate calls to stay under the free-tier RPD/grounding quota.
- `chart.py` — matplotlib chart saved as 3 aligned layers (0 axes, 1 candles, 2 levels) so video.py can animate the reveal. Layers must stay pixel-identical in layout.
- `video.py` — Pillow draws frames, piped as raw RGB to ffmpeg (imageio-ffmpeg binary). Each scene subclasses `Scene` with `key(t)` (cache key; quantize animation so frames can be cached) and `draw(d, L, t)` onto an RGBA layer. `Backdrop`, `Ticker`, header, captions, progress line composed in `render()`. `scenes_from_plan()` builds the scene list from a `ShortsPlan`: `HookScene`, `NiftyScene`, `OutroScene`, and `RowsScene` for everything else. A scene must never draw a string the plan didn't declare - `plan.public_text()` is what the content scan and the reading budget see.
- `music.py` — procedural copyright-free track with swells at scene boundaries; rotates through 5 mood/tempo presets by calendar date (`_variant_index`) so consecutive sessions don't sound identical. `assets/music.mp3` overrides with one fixed track every day; `assets/music/1.mp3`..`5.mp3` overrides one real track per rotation slot. Playback volume is `config.MUSIC_VOLUME` (env `MUSIC_VOLUME`, default low ~0.22), applied in `video.render()`'s ffmpeg audio filter.
- `upload.py` — YouTube Data API v3 upload.
- `config.py` — all settings/env vars, colours, `fmt_in()` Indian number formatting.
- `core/` — canonical domain: `Observation` (what one source said, frozen), `Fact`, `ValidationResult`, `MarketReport`, `sources.py` (`SourceMetadata` + independence groups), the validator framework, and `content_safety.py`. No fetching, no drawing.
- `providers/` — acquisition layer (Phase 2). Wraps the existing `market.py`/`news.py` fetching; above this line everything is an `Observation` or a typed payload, never a raw provider dict. `yahoo.py` (+ `IndexSession`), `nse.py`, `news.py` (+ `NarrativeBundle`), `gemini.py`.
- `adapters/` — dict→Observation translation and `report_builder.build_report()`, which groups observations into validated facts and assembles the `MarketReport`.
- `presentation/` — `ReportPresentation` converts a `MarketReport` into the exact structures `video.py`/`chart.py` already accept. The renderer acquires nothing.
- `storage/` — SQLite historical index (Phase 3): `schema.py`, `migrations.py` (PRAGMA user_version), `repository.py` (`MarketHistory`, all SQL lives here). Defaults to `output/data/market_history.db`.
- `editorial/` — Phase 4.1.2: turns the report + snapshot into a `ShortsPlan` - what the Short says, in what order, for how long. `config.py` holds every readability/pacing constant, `hook.py` picks the opening fact deterministically (no LLM), `readability.py` estimates reading time and sets durations, `planner.py` builds the scenes. Derived, never canonical; mutates neither input. See `docs/SHORTS_EDITORIAL.md`.
- `intelligence/` — Phase 4.1 deterministic historical context: `models.py` (`IntelligenceSnapshot`, eligibility policy), `history.py` (`HistoricalWindow`: exclusive cutoff, session semantics, bulk loading), `engine.py`, and the analysers (`market_context`, `flows`, `sectors`, `movers`, `volatility`). Reads the canonical report + `MarketHistory` only; writes `output/intelligence/`. See `docs/INTELLIGENCE.md`.
- `hooks/` — Dynamic Hook Engine (hook Phase 1): the first 4-5s of the Short for PRE_MARKET / POST_MARKET / CUSTOM_SINGLE_STOCK. Sheet builders turn validated inputs into `HookFact`s + approved teaser beats; `candidates.py` builds 1-5 deterministic candidates over 7 archetypes (templates self-validated); `gemini.py` makes one structured, un-grounded Gemini call to choose candidate/hero/beats and write the curiosity + summary lines; `validation.py` checks every line and choice; `engine.plan_hook()` always returns a `HookPlan` (deterministic fallback). Rendered by `daily_video/hook_scene.py` (`DYNAMIC_HOOK`) with the generic motion toolkit `daily_video/hook_kit.py` (paper slips, neon ring/underline, stamps, tape, masked number rise): visuals key on beat kind / hero visual only, never on a symbol, and never count a number up through unvalidated values. CUSTOM has a hook only; PRE has its V1 Short (`docs/PRE_MARKET.md`). See `docs/HOOK_ENGINE.md`.
- Market Radar in the unified Short (Phase 2): `presentation/radar_story.py` builds a `RadarStoryModel` per story (one event, <=2 prices, exactly ONE supporting fact: detector-flagged volume first, else close location in the day's range; fixed-template takeaway; no relative strength on screen) and `daily_video/radar_story_scene.py` draws it in one shared chart-first shell (real OHLC candles from `RadarVisualEvidence.open/high/low_series`). The POST Short publishes the selector's first `RADAR_PUBLISH_LIMIT` (3) stories in selector order - never a second selector; the rest go to `omitted`. The Radar intro scene is locked (a test pins its source hash). A story with no validated technical event is never drawn as an event: VOLUME family (detector-flagged volume: neutral candles + volume histogram hero + prior-20 average line; "Trading volume was unusually high while price finished 0.7% lower.") or SESSION family (day-range strip). Nothing may say something changed "on the chart" without an event. Visible direction (badge, close tag, higher/lower) always comes from `price_change_pct`, never from the internal `direction` / `direction_label` / selection reason (internal-only; COROMANDEL 24 Sep was ALIGNED_POSITIVE on a -0.69% day). See docs/SHORTS_EDITORIAL.md.
- POST editorial plan (Phase 3): `presentation/post_plan.py` `plan_post_sections()` deterministically decides which sections the POST Short contains (core: market pulse, sectors, Radar; optional - Nifty chart only on a NEW structural event, movers only if distinct from Radar and large (a single move >= 7% or a top gain vs top fall spread >= 12 pts - POST freeze; 4%/6 pts fired on ~90% of sessions), flows, same-day global context, high-impact event - at most 2 optional, each must add a fact no core section carries) with a written reason per section. The storyboard lays it out; `daily_video/market_scenes.py` draws it. "Overnight global cues" is a PRE topic and never a routine POST section. Never ask Gemini which sections appear. See docs/SHORTS_EDITORIAL.md.
- PRE-MARKET V1 (`docs/PRE_MARKET.md`): `python main.py --mode premarket` (router: `products/__init__.py` `VideoRequest` + `route()`; POST stays the default and runs `main.run` unchanged). `products/premarket.py` loads the PREVIOUS session's canonical report from `MarketHistory` (never rebuilds/re-saves it), `providers/premarket.py` acquires dated/timestamped pre-open readings (US closes, Nikkei/Hang Seng live 5-min bars, India VIX change by canonical date; GIFT Nifty from the exchange itself - `providers/gift_nifty.py`, NSE IX near-month future vs its previous daily settlement file, wired by `build_real_brief` through the `gift_fn` seam), `core/freshness.py` judges them, `core/event_calendar.py` holds verified schedules only (2026 FOMC in code; RBI MPC 2026-27 in the controlled file `data/official_events.json`, re-checked by `verify_official_events.py`; F&O expiry rule), every PRE run is recorded in `publication_runs` (mode `PRE_MARKET`, `products/pre_run_history.py`), `presentation/pre_provenance.py` audits every PRE fact, `presentation/pre_plan.py` `PreEditorialPlanner` decides sections deterministically (core: overnight, previous-session setup, event, watch-at-the-open; optional <= 2 of stock watch/flows/VIX/sectors), `daily_video/pre_storyboard.py` + `pre_scenes.py` render with the POST design system and the approved hook engine. `render_pre_phase1.py` -> `output/pre_phase1/` (real reconstructions + SYNTHETIC scenarios); `validate_pre_data_sources.py` -> `output/pre_data_sources/`. V1 never uploads.
- Production scheduling (docs/PRODUCTION_SCHEDULE.md): REPORT (19:30 IST, D) -> PRE (07:30, D+1) / POST (07:40, D+1). `main.produce_report` is the ONE report-building path; `products/report_job.py` wraps it (REPORT job) and `main.obtain_post_report` reuses the canonical report or falls back to it (`BUILT_INLINE`, recorded). `operations/`: `sessions.py` (calendar session resolution: `latest_final_session`, `edition_date_for`), `report_lookup.py` (`find_canonical_report`: exact session, artifact present/parsable/matching, never a substitute), `gift_policy.py` (GIFT display gate, default OFF), `connectivity.py`, `official_events.py`. GitHub: `market_report.yml`, `pre_shadow.yml`, `connectivity.yml` share state via `actions/cache` + one concurrency group; `daily_byte.yml` (POST) is unchanged during the shadow period.
- RADAR_SELECTED vs RADAR_PUBLISHED (PRE shadow readiness): the REPORT job's Radar only SELECTS (`editorial_selections`); a story is PUBLISHED only by `products/radar_publication.confirm_radar_publication` after a completed POST artifact passes every QA gate (`radar_publications`, editorial DB v2; once per session, reruns are no-ops; only rendered stories; demo never). The selector's cooldown and PRE stock watch read published only. The scheduled POST (`main.run`, legacy `video.py`) has no Radar section, so it publishes none (recorded in run `details.radar`); `render_daily_market_byte.py --confirm-publication` is the opt-in path until the POST cut-over. See docs/PRODUCTION_SCHEDULE.md.
- `operations/gemini_smoke.py` (one real, un-retried hook-contract request; key only in the header, redacted everywhere) and `operations/stray_cleanup.py` (one-off, property-matched removal of known test contamination with backup + audit; `MarketHistory.remove_contaminated_runs` is manual-only, ast-guarded out of main.py/products).
- `qa/` — deterministic post-render artifact checks (`check_video`, `write_qa_artifact`). No model involved. `probe_media`/`sample_frame_stats` are the one mockable media seam.
- `tests/` — `pytest`, fully offline (incl. an end-to-end run of the production branch with every network boundary stubbed). `python -m pytest tests/ -q`.
- `docs/` — ARCHITECTURE, DATA_MODEL, VALIDATION_RULES, SOURCE_PROVENANCE, MIGRATION_PLAN, CONTENT_SAFETY, INTELLIGENCE, SHORTS_EDITORIAL, STORAGE, PRODUCTION_QA, HOOK_ENGINE, PRE_MARKET, PRODUCTION_SCHEDULE, NSEIX_RIGHTS_REVIEW. Update these in the same commit as any architecture-affecting change.
- `core/content_safety.py` — Phase 1.1: deterministic (no Gemini) recommendation-language filter. `apply_content_safety()` in `main.py` sanitizes/drops mover reasons, the Nifty move summary, and event text before any scene or caption is built; `scan_publication()` re-scans every finalized caption/title/description immediately before upload and blocks it (never rewrites) if anything survives. See `docs/CONTENT_SAFETY.md`.

## Rules / decisions (keep these)
- No paid APIs. AI = Gemini free tier only (`GEMINI_API_KEY`, `GEMINI_MODEL`). Pipeline must still work with no key.
- An LLM is never a source of truth for a critical numeric market fact. Everything Gemini returns is `SourceType.AI`, and `core.validation` refuses to mark a critical metric (index/stock/sector moves, closes, levels, FII/DII, commodity, FX) `VERIFIED` when only AI observations back it — its ceiling is `PROVISIONAL`, and two agreeing Gemini answers are still `PROVISIONAL`. Passing a range check is NOT verification: a plausible wrong number passes. AI values reach `VERIFIED` only when an acceptable non-AI source independently agrees within tolerance. The rule lives in `CrossSourceValidator` so no new caller can skip it.
- Source authority is NOT source independence. `source_type` says how much one source's word is worth; `independence_group` says whether two readings are separate evidence at all. `CrossSourceValidator` counts INDEPENDENCE GROUPS, never observations — two Yahoo readings of one close are one witness, and two Google News items from one publisher are one witness. Never let a same-group pair produce `VERIFIED`. News groups by publisher (`news_source()`), not by the aggregator.
- The MarketReport is authoritative (Phase 2). It is built BEFORE anything is rendered, `check_publication()` makes `publication_ready` binding (an unfit report writes its JSON for diagnosis and renders nothing), and the renderer is fed from it via `presentation/`. The presentation invariant: IF A NUMBER IS DISPLAYED IN THE VIDEO, IT EXISTS IN THE MARKETREPORT — including the chart's candle series (`technicals.candles`). The adapter may reshape and format; it must never fetch or compute a market fact.
- Publication needs THREE gates to pass, none advisory: data QA (`report.publication_ready`), content QA (`core.content_safety`), video QA (`qa.check_video`). Persistence is a fourth precondition — if the run can't be recorded in history, it doesn't publish, because auditability is part of publication integrity. Failure never deletes artifacts: the video, metadata, report JSON and QA artifact are all preserved for diagnosis.
- JSON is the immutable per-run artifact; SQLite is a queryable index ACROSS runs that points back at those files (`json_artifact_path`). SQLite is never in the render path — a database problem must not be able to change what a video looks like. Persisting an existing `report_id` is a no-op (reruns must not duplicate canonical history); `publication_runs` always appends. Demo runs persist with `is_demo=1` and are excluded from every query by default.
- CANONICAL HISTORY IS IMMUTABLE once persisted. A report says what the market did; video QA, the final content scan and the upload result say what happened when we tried to publish it — the second must never rewrite the first. Per run the JSON is written ONCE and `save_report` is called ONCE; later verdicts go to `publication_runs` and the QA artifact. Never re-save the report JSON or call `save_report(replace=True)` from the pipeline — `replace=True` deletes and cascades, and exists only as a manual recovery tool (a test parses `main.py` with `ast` and fails if any call there passes it). Content safety has two stages: Stage A sanitises BEFORE the report is finalized (canonical, in `report.content_safety`); Stage B is the final publication scan (operational, blocks upload, never written back into the report).
- Historical intelligence is DETERMINISTIC and DERIVED. No LLM computes a streak, percentile, average, rank or classification — rules only, so the same report + database always gives byte-identical output. It acquires nothing (no provider/network/model; a test greps the package for those references) and mutates nothing (canonical JSON and rows are untouched). It never predicts, ranks securities or recommends. Enforce: the current session is excluded from its own comparison window; windows count TRADING sessions (weekends/holidays are not missing sessions); only `{VERIFIED, SINGLE_SOURCE}` facts are eligible (`ELIGIBLE_HISTORICAL_STATUSES`, centralised); relative volume compares only `definition_version == "2.0"` readings; a statistic defined as N sessions makes NO statement with fewer than N (never silently shorten); sector returns compound, never sum. STREAKS are continuity claims: they walk the canonical session spine (`get_recent_sessions`, independent of eligibility) and BREAK at any recorded session that is opposite/zero/missing/ineligible — never step over one to find another matching value. Calendar gaps (weekend/holiday/never-recorded) aren't on the spine so they can't break a run: a missing calendar day is not missing canonical evidence. Streaks say "consecutive recorded sessions"; cumulative flow keeps separate "available sessions" semantics. Relative-volume history dedupes to `(report_id, fact_id)` — counting observations would inflate the sample and rank. Every insight must carry sample size, lookback and supporting report/fact ids.
- Relative volume = current volume / mean of the PRIOR 20 sessions, current session excluded, `None` below 20 priors (definition_version 2.0; reports before Phase 3 used 10 and are NOT rewritten or backfilled — the definition travels on each observation's metadata). Don't silently compute over a shorter window and call it the same metric.
- Provenance is recorded at acquisition, never reconstructed downstream. `news.ai_pass` stamps each reason/event with the branch that produced it (`GEMINI`/`GOOGLE_NEWS_RSS`/`RULE_FNO_EXPIRY`/`NO_VERIFIED_CATALYST`), and `nse_all_indices` keeps NSE's market timestamp, which becomes `Observation.observed_at`. Don't reintroduce string-matching to guess where text came from — only the acquisition layer can still see it.
- Don't rewrite a legacy module to make new code prettier — adapt at the boundary. Provenance must be honest: an unavailable source is `None`, never a plausible guess.
- Daily Market Byte must never republish recommendation-style language (BUY/SELL/target price/stop loss/multibagger/etc.) picked up from a headline or brokerage note, even as a quoted fact. `core.content_safety` catches this deterministically (no Gemini — the guarantee must hold even when the AI layer is down) at two points: sanitize-on-generation for every mover reason/event/Nifty summary (BLOCKED text gets a neutral fallback, never the raw headline), and a final re-scan of every finalized caption/title/description immediately before upload that blocks publication (never rewrites) if anything unsafe survives. An attributed third-party rating ("MOFSL initiates BUY rating with target Rs 1,500") is neutralized to a fixed factual template rather than blocked outright, so ordinary brokerage-coverage news doesn't need to be dropped entirely.
- Accuracy over completeness: never post unverified numbers. Nifty close is cross-checked (NSE or Gemini) and the run aborts if >0.2% off. AI-sourced numbers must pass date + sanity-range checks or be hidden. A failed optional scene (global, fii, sector) is simply dropped and the Short is shorter - nothing stretches to fill a fixed budget.
- Don't trust a single data source blindly just because the fetch succeeded - verified 2026-09-18: yfinance's `BZ=F` (Brent crude) ticker returned -5.28% vs an independently-reported -1.54% real move (a ~4x error, likely a thin/mismatched contract). DOW/NASDAQ/GOLD/USD-INR were cross-checked the same day and matched real sources closely, so this isn't a general yfinance problem - it's specific to that ticker. Brent is now sourced only via `news.market_facts()`'s Gemini-verified `"brent"` fact (same hide-if-unverified pattern as GIFT Nifty), not `market.GLOBALS`. Before trusting any new single-sourced number in this pipeline, cross-check it against an independent source first.
- Mover "reason" headlines (`news.explain_moves`) must be filtered by both the headline's RSS `pubDate` (`_same_day`) and a date pattern embedded in the title text itself (`_title_date_ok`) before being used - verified that recurring "Stocks to Watch Today, <date>:" listicle columns get republished daily with a fresh `pubDate` but keep a stale headline (e.g. crawled 19 Sep, title still says "Aug 3"), and Google News' relevance ranking put that ahead of genuinely same-day coverage. Never take `headlines[0]` un-filtered as a mover's reason.
- Never compute a day-over-day % change as `Close.iloc[-1] / Close.iloc[-2]` without first checking `iloc[-2]`'s DATE matches the expected previous trading session - verified 2026-09-18: yfinance's per-stock bulk download (`get_movers`) silently dropped 17 Sep entirely for ~25% of the Nifty100 universe (e.g. ADANIGREEN), so `[-2]` quietly pointed at 16 Sep, turning a 2-day move into a false 1-day one (shown +5.06%, real +4.73%). `market.get_movers`/`get_sectors`/`get_market`'s Bank Nifty calc now all take the actual previous session date (`analyze()`'s `prev_date`, from the Nifty index's own reliable calendar) and drop/skip anything whose own previous-close date doesn't match it, rather than risk a silently-wrong multi-day change. Apply the same date-alignment check to any new day-over-day calculation added to this file.
- Provider rows never define trading sessions (session-alignment patch). `core/trading_calendar.py` is the canonical NSE session rule: benchmark index bars ∪ weekdays not on NSE's published holiday list ∪ listed special sessions. For years the list doesn't cover, it falls back to the benchmark bars. Verified 2026-09-25: per-stock Yahoo feeds carry fake placeholder rows on real holidays (2026-05-01/05-28/06-26/09-14: O=H=L=C = prev close, volume 0). Those aborted the next session and inflated RVOL on 60 sessions. Separately, every Yahoo Indian INDEX feed is missing Tue 2026-09-22, which was a REAL session, so the index-bar spine alone is not canonical. Every day-over-day or window calculation drops non-session rows BEFORE any positional `[-2]` read (`market._prepare_series`/`_drop_non_sessions`, `radar.session_alignment`). The previous close is the canonical previous session. If the benchmark lacks that session, `get_market` raises `SessionAlignmentError` (session-level) rather than publish a two-session change as a daily move. A bad or missing symbol is only ever symbol-level. Add NSE's next-year holiday list every December. See docs/VALIDATION_RULES.md section 9.
- Benchmark gap recovery (second index source): a canonical session the Yahoo index series lacks (verified: every Yahoo Indian index feed misses Tue 2026-09-22) is filled by `market.recover_index_gaps` from NSE's end-of-day index file (`ind_close_all_DDMMYYYY.csv`) - only when the calendar says the session existed, only for gaps INSIDE the primary series, and only if the row validates (dated right, sane OHLC, implied previous close = adjacent canonical close within 0.05%, stated % agrees). Never interpolate, never infer from stocks, never write it into the Yahoo OHLCV cache. Every attempt is a provenance record (`session_alignment.benchmark_recovery`, `previous_close_source`); a rejected fallback on the previous session still raises `SessionAlignmentError`. See docs/VALIDATION_RULES.md sections 10-11.
- Recap-session recovery (owner decision, POST final edge-case patch): when Yahoo lacks the RECAP session itself (verified: the 23 Sep 07:40 run saw only 21 Sep), `market.recover_recap_session` takes it from the same NSE end-of-day file. Conditions: the calendar covers the date and calls it a session; the session is FINAL (`SESSION_FINAL_TIME` passed; a session in progress is never fetched or used - no fallback intraday); the row validates and anchors on the previous canonical close; at most 2 trailing sessions. The close is then observed as `nse_index_close_archive` (PRIMARY, group NSE), never as Yahoo. If Yahoo and NSE both fail on a real session, `main.collect` raises `SessionAlignmentError` (BENCHMARK_MISSING_RECAP_SESSION) and the run is BLOCKED - never a silent holiday skip. India VIX is date-checked against the recap session. See docs/VALIDATION_RULES.md section 10.1.
- `market.SESSION_FINAL_TIME` (15:40 IST) is the one "bar is final" rule (`_clean`, write-through guard, `radar.cache_repair`). Cached non-final rows are repaired only by `radar.cache_repair` (conditional per-row replace, read-back, NSE bhavcopy check). `CandidateHistoryStore.invalidate_sessions` + `spine_repair_range` are manual history-repair tools (like `save_report(replace=True)`): never call them from the daily pipeline.
- yfinance's bulk `yf.download()` endpoint can return the latest session's row with Open/High/Low/Volume populated but `Close` still `NaN` - verified 2026-09-22: effectively the whole NIFTY100 universe showed this for 21 Sep, still unresolved several minutes (and multiple retries) after that session's close, i.e. this can be a persistent Yahoo-side backfill lag, not just a few-second blip. `_clean()`'s `dropna(subset=["Close"])` correctly drops that unusable row, which silently pushed every stock's "latest row" back to the prior session and made `get_movers` find zero movers for `recap_date`. `get_movers` now distinguishes this signature (the row for `recap_date` exists pre-dropna, just with a NaN Close) from a stock with no data at all, and retries the whole batch fetch up to 2 more times with a 30s/60s wait before giving up - this fixes a short-lived lag but NOT one that persists for minutes, in which case the `RuntimeError` is correct (never publish gainers/losers built from an incomplete close) and the right recovery is to re-run later or let the next scheduled cron pick it up once Yahoo has backfilled, not to add more in-process retries.
- Skip upload if yesterday was a market holiday (latest session != previous weekday).
- MARKET REPORT GENERATION IS ITS OWN JOB (PRE production scheduling). The REPORT job builds session D's canonical report after the close; POST and PRE consume it and never rebuild it. One report per session: `report_date` is the EDITION (the next canonical session, `operations.sessions.edition_date_for`) - identical to what the 07:40 run always produced - so an evening build and a morning fallback share one report_id. The REPORT job never builds a session that is not final or not on the calendar, never builds from a benchmark that ends on an older session, and does NOT commit a report that fails data validation. ONE CANONICAL RULE (owner-approved, PRE shadow readiness): `main.may_become_canonical` - an unfit MarketReport never becomes canonical, whichever job built it (REPORT job or POST inline fallback); it goes to `reports/unfit/`, the run is BLOCKED at DATA_QA, and a retry may build a fit one (a transient data gap must not lock an invalid immutable record). Enforced in `produce_report` and again in `persist_report`; demo exempt. An evening build drops Gemini's "GIFT Nifty this morning" (`collect(morning_facts=False)`) - it cannot exist yet. POST reuses the canonical report (`REUSED_CANONICAL`) and builds inline only when it is missing (`BUILT_INLINE`, recorded); a POST render failure never touches the report.
- PRE previous-session rule: `products.premarket.require_previous_report` - the calendar's previous session exactly, a readable matching artifact, publication-ready; else BLOCKED (`PREVIOUS_SESSION_MISSING` / `PREVIOUS_REPORT_UNUSABLE` / `PREVIOUS_REPORT_NOT_PUBLICATION_READY`); a non-session PRE date is SKIPPED. Never an older report.
- GIFT Nifty display is behind `operations/gift_policy.py`, DEFAULT OFF: `GIFT_NIFTY_PUBLICATION_ENABLED=true` AND a non-empty `GIFT_NIFTY_PUBLICATION_APPROVAL` reference are both required - the endpoint working is not permission (docs/NSEIX_RIGHTS_REVIEW.md: rights OPEN). Gate closed: publication mode does not fetch GIFT; shadow mode fetches + validates + audits it (`gift_audit_<date>.json`) and removes it from the brief so nothing can show it. A policy withhold is never a degradation; an unreachable GIFT is DEGRADED, never BLOCKED. Never commit real NSE IX payloads to tests/fixtures (synthetic, structurally identical responses only).
- Run history distinguishes jobs: `publication_runs.job_type` (REPORT_BUILD / POST_MARKET / PRE_MARKET, schema v3) + `source_session_date`; legacy rows derive their job from `mode` on read and are never rewritten. Every POST/REPORT close sets `run_status`; an unexpected crash closes the run as FAILED (`main._fail_open_run`).
- Keep the on-screen and description disclaimer ("For information only - not investment advice"). No buy/sell language, no predictions in captions (SEBI).
- A valid fact does not earn screen time. The canonical report keeps everything; `editorial/` decides what the Short shows, and what it drops is recorded in `plan.omitted`, never removed from the report or from history. Selection and scene ordering are deterministic - never ask Gemini what matters.
- POST freeze - no ranking over a partial universe. `market.get_movers_audited` records `universe_expected / universe_observed / universe_validated / coverage_pct` (= validated / expected) into `report.metadata["movers_coverage"]`; `editorial/movers_gate.py` publishes Movers / top-gainer / top-loser claims only at coverage >= `MOVERS_MIN_COVERAGE_PCT` (90). No coverage record (every report built before the gate) = UNKNOWN = suppressed. Suppression is recorded in `plan.omitted`, never removed from the report. Verified 2026-09-21: a report ranked its movers over a partial Yahoo batch (top gainer shown +1.90%, the full universe had +3.83%).
- POST freeze - every single-stock move passes `core/move_guard.validate_move` before it can be a Movers row, a top-gainer/loser claim or a published Market Radar story (`presentation/radar_guard.py`, applied before `RADAR_PUBLISH_LIMIT`; the selector's ranking/detectors are untouched, the next story moves up). Held: missing/stale previous close, self-contradicting bar, stated % not matching its closes, a split/bonus ratio at the open, any |move| >= 20% (single source, no corporate-action feed - verified: VEDL -64.9% on 30 Apr 2026 and a -36% print on 24 Sep were both unresolvable), a >= 10% move without >= 1.5x volume. Raw values stay in the audit. Never hard-code a symbol in the guard.
- POST freeze - hook priority: on |Nifty| >= 1.5% the BIG_MOVE hook outranks a single-stock UNUSUAL_ACTIVITY hook; the stock candidate is not even offered to Gemini unless it is objectively exceptional (|move| >= 10%, rvol >= 5x and |move| >= 5x |Nifty|, all on validated facts - `hooks/policy.py`). POST teaser beats: one beat per entity, different families preferred, played index -> sector/flow -> stock; fewer beats rather than a repeat (`hooks/diversity.py`; Gemini picks that repeat an entity fail validation).
- The ONE exception (owner decision, hook Phase 1): in `hooks/`, Gemini may CHOOSE the opening among 1-5 deterministic, pre-approved candidates (and 2-3 approved teaser beats) and write the curiosity + summary lines. Eligibility, scores, heroes and beats stay deterministic. Every Gemini line is validated (numbers must belong to the fact of the entity they are written next to, entities must exist, no causal/prediction/recommendation/hype words, characterisations need a deterministic claim, the summary may promise only sections the Short has); a failure falls back to the deterministic template - the video never fails because Gemini failed. The same validator runs on our own templates. Don't widen Gemini's role beyond choosing and wording.
- `trim_to_fit` drops rows from the END of a scene, so order every scene's items so trimming costs the optional extra, never the point of the scene. Sectors are `[strongest, weakest, runner-up]` and movers `[best gainer, worst loser, runner-up]` because ranking either purely by size of move produced a scene that lost its contrast - three gainers under "Biggest moves", or a sector scene with no weakest sector.
- Don't state a statistic that carries no information. A rank is only worth its line near either end of its window ("Bigger move than 0 of the last 20 sessions" is true and reads on screen like a failed lookup); `_rank_line` returns "" in the middle and the caller falls through to something that does say something.
- Layout must stay in the Shorts safe zone: content between y≈340 and 1195, captions box y 1215–1475, nothing important on the far right below y≈1100. Canvas 1080x1920, 30 fps. The strip below the disclaimer (y≈1524–1920) is left empty on purpose - reserved for the YouTube Shorts app's own UI overlay (title/channel/audio-track/like-comment-share). Don't add content there - this is a financial/informational video, not a music-video style visualizer.
- `SECTION_Y` (video.py) is load-bearing: `NiftyScene` hardcodes its chart paste relative to it rather than deriving it, so don't shift `SECTION_Y` without re-checking the chart still fits above y≈1195.
- Text must fit: use `fit()`, `ellipsize()`, `wrap()`; reasons are clipped to ~13 words.
- Rupee sign via `video.RS` (falls back to "Rs " if the font lacks ₹).
- Demo data must use placeholder names (STOCK-A...) so it can never be mistaken for real data.

- PRE-MARKET rules (V1): a pre-open number is shown only when FRESH (`core/freshness.py`) and every LIVE reading shows its IST time; GIFT Nifty is a timestamped past-tense fact ("GIFT Nifty was 0.60% lower at 7:52 AM IST", "VS ITS THU SETTLEMENT"), never "points to"/"will open", never compared with Nifty's spot close, and never from Gemini. GIFT = NSE IX near-month NIFTY future (earliest expiry on/after the session) vs NSE IX's previous Daily Settlement Price file; shown only if <= 20 min old, taken before the 09:15 open, and the exchange's own DAYCHANGE implies the same settlement (else CONFLICT) - a failure omits it and never blocks. A reconstruction of a past morning never shows GIFT (the live reading is after the cutoff: FUTURE). Official schedules come only from the organiser's own publication, entered in `data/official_events.json` with URL, release number, quoted line, retrieved_at and verified_on; the loader fails closed (off-host source, dates vs quoted line mismatch, a time without a quoted time source, verification > 180 days old) and the daily run never fetches the organiser's site. No displayed PRE fact may have AI provenance (`render_pre` provenance gate); AI-only FII/DII or sectors are dropped from PRE. Every PRE run - SUCCESS/DEGRADED/BLOCKED/FAILED/SKIPPED - is recorded in `publication_runs` (schema v2: `target_date`, `run_status`; v3: `job_type`, `source_session_date`) with its degradations; recording is never fatal. The previous-session setup is always labelled with its day ("YESTERDAY'S SETUP" only when it literally was yesterday; Monday says "FRIDAY'S SETUP"). A PRE event must be a verified schedule (`OFFICIAL_SCHEDULE` with source page + check date, or `RULE_DERIVED` on the canonical calendar); news headlines in `report.events` are never "today's event". Watch-at-the-open cards are facts with a day/time, never actions. Stock watch carries forward at most 2 of the previous session's PUBLISHED Radar stories (the `radar_publications` ledger, on-screen order) - never merely SELECTED ones; no overnight stock selector. `pre_language_issues()` (hook word lists + PRE phrasings like "open higher", "continuation", "rally", "hold", "watch for", ", so") blocks the render on any hit. If the previous session's canonical report is missing or describes another session, PRE is BLOCKED - an older session is never shown as "previous".
- "Events today" (`news.todays_events`) must be specific, named events only - IPO opens/GMP, company results/corporate actions, RBI/govt decisions, Fed/global data - never generic daily "roundup" columns (Ahead of Market, Stocks to Watch, Market Wrap, etc., which just reuse the same catch-all title every day and aren't actual events). Both the Gemini prompt and the no-key fallback (`_fallback_events`, targeted per-category queries filtered through `_GENERIC_ROUNDUP`) must keep excluding those.

## Known limitations
- NSE website often blocks cloud IPs (GitHub runners) → FII/DII and sector data fall back to Gemini / Yahoo.
- GIFT Nifty: POST still gets it only via Gemini search (hidden if unverifiable). PRE reads NSE IX's undocumented website API (shape can change -> omitted; display rights unreviewed; reachability from GitHub runners unverified; the morning DAYCHANGE reference is enforced at runtime but was verified live only on the evening session). RBI MPC dates are a hand-maintained file: re-run `python verify_official_events.py --stamp` when RBI publishes the next year's schedule (and at least every 180 days).
- YouTube uploads are private until the Google Cloud project passes the API audit. OAuth consent screen must be "In production" or tokens expire after 7 days.
- GitHub cron can start 5–20 min late; runs take ~4–6 min.
- GitHub runners are ephemeral: the REPORT job's canonical report reaches the next morning's PRE only through the `actions/cache` state (`daily-byte-state-*`, evicted after 7 days unused - not archival). `daily_byte.yml` (POST) does not restore that state yet, so on GitHub POST still builds its report inline each morning until the post-shadow cut-over (docs/PRODUCTION_SCHEDULE.md).
- Nifty 50 fallback constituent list in market.py goes stale; the live NSE CSV is preferred.
- Gemini's `generateContent` (`news.ask_gemini`) intermittently 404s/503s even with a valid key/model/project - confirmed as a known, unresolved server-side Gemini API bug (Google's own developer forum, Sep 2026 - same request sometimes succeeds, sometimes 404s, across different projects/keys). Not a sign the model name or key is wrong. `ask_gemini` retries those (5x, capped backoff) and logs the response body on failure; if it still fails, `ai_pass` already degrades gracefully - AI-only facts (GIFT Nifty, Brent, verified FII/DII) are simply omitted and reasons/events fall back to the non-AI paths, never a guess. This is by design, not a bug to "fix" further without a real Google-side change.
- A Gemini 429 ("You exceeded your current quota...") is a different failure from the 404/503 bug above - it's the free-tier RPD/RPM (or grounding) quota exhausted, not a transient server hiccup, so retrying within the same run can't succeed. `ask_gemini` fails fast on 429 (no backoff loop, unlike 404/503) straight to the same graceful no-AI-facts fallback. `news.ai_pass()` already merges what used to be three separate Gemini calls per run (`market_facts`/`explain_moves`/`todays_events`) into one request to stay under the free-tier quota; if 429s still recur daily, the remaining fix is upgrading the API plan/billing, not retrying harder or adding calls back.
